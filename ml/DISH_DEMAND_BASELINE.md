# Per-dish demand baseline

**Goal:** predict the number of portions sold for each dish at the next service. These forecasts are inputs to preparation planning. They are not preparation recommendations by themselves.

The public [Restaurant Sales Data with Features](https://data.mendeley.com/datasets/xv5kp6mxv7/1) by Fabian Taigel contains daily observed servings sold for seven dishes at one restaurant. The source is licensed CC BY 4.0. `data/restaurant_dish_sales.csv` extracts only the date and seven observed sales counts from `data_preprocessed.csv`: 760 service dates from 2013-10-04 to 2015-11-07, or 5,320 dish-day rows. `prepare_dish_data.py` reproduces the extraction from the source ZIP. The source archive was downloaded from `https://data.mendeley.com/public-api/zip/xv5kp6mxv7/download/1`; its SHA-256 is `a4016267e92dde57418ede8d0780db0295f9311e036dfb97e2b4ca75e2d46ce2`. The extracted CSV SHA-256 is recorded in `dish_demand_report.json`.

From this `ml` directory, after `uv sync --locked`:

```sh
uv run --locked python train_dish_demand.py
uv run --locked python train_dish_demand.py --predict-date 2015-11-08
```

Training writes `dish_demand_report.json` and `dish_demand_model.joblib`. The binary model is ignored by Git and regenerated by the first command. The forecast command uses `--data` as observed history and requires a future `--predict-date`. Forecast values are expected portions, so they can be fractional; any prep rule must decide how to round and account for capacity, costs, and shortages.

For another stable menu, pass `--data` a CSV with `date,dish,sold` columns and at least 60 service dates. Dates must be ISO format; counts must be nonnegative integers; there must be one record for every dish on every service date. Retrain on that restaurant's history before forecasting its dishes. A missing record must be resolved explicitly: absence from the menu is different from zero sales. A new or changing menu needs a separate cold-start treatment.

The model uses dish identity, calendar date, and prior observed sales, including previous service, recent 7 and 28 services, and recent same weekdays. It never uses sales from the target service. Calendar gaps are left as gaps. Three candidate models are compared on a chronological validation period; only the selected model is evaluated on the final holdout period. The selected Extra Trees model is refit on all history for future forecasts.

| Final holdout, 152 services / 1,064 dish-days | MAE (portions) | RMSE (portions) |
|---|---:|---:|
| Extra Trees | 4.78 | 7.08 |
| Previous four same weekdays | 5.21 | 7.68 |

These figures evaluate sales prediction at this one restaurant. The dataset has no covers, prepared quantities, ingredient costs, stockout indicators, or service-time availability. Recorded sales can understate demand if a dish sold out. Therefore this model does not measure waste reduction or missed sales, and a fitted model from these seven dishes cannot be reused unchanged for arbitrary restaurants or products. The workflow and features can be reused after local retraining and validation. The separate inventory modeller in this directory works at restaurant-level kilograms and addresses a different, aggregate target.
